# MsgPacketizer システム仕様とトラブルシューティング記録

## 概要
Arduino/MCU 側で `MsgPacketizer` ライブラリを使用してシリアル通信を行う際、C++（PlatformIO）側の必須ビルドオプションと、Raspberry Pi（Python）側で正しくデータを受信・送信するための仕様、およびデバッグで判明したトラブルの根本原因を記録する。

## C++ (PlatformIO) 側の必須ビルドオプション (`platformio.ini`)

MsgPacketizer および内部で使用される MsgPack は、マイコンの貴重なメモリ（RAM）を節約するため、静的なメモリ確保を行っています。そのため、デフォルトではかなり厳しい要素数・登録数の上限が設定されています。
今回の GSE/サテライトシステムでは扱うデータ量や通信ポートが多いため、`platformio.ini` の `build_flags` にて以下のマクロを定義して上限を拡張しています。

### 1. `-D PACKETIZER_MAX_STREAM_MAP_SIZE=4`
- **概要:** MsgPacketizer が同時に処理（監視）できる通信ストリーム（`Serial` や `Serial1`、`Wire` など）の最大登録数を指定する設定。
- **解説:** 今回のシステムでは、LaunchController が「デバッグ・RasPi通信用のUSB (`Serial`)」と「サテライト通信用のRS485 (`Serial1`)」の **2つのシリアルストリーム** を同時に監視・パースする必要があります。デフォルトの上限設定（通常は1か2）では複数ポートの同時登録が弾かれてしまうリスクがあるため、安全率を見込んで最大 `4` ストリームまで処理できるように拡張しています。
- **影響:** この設定が不足していると、後から登録したシリアルポートからのパケットが無視され、`MsgPacketizer::update()` を呼んでもコールバックが一切呼ばれなくなるという原因不明の通信不良に陥ります。

### 2. `-D PACKETIZER_MAX_CALLBACK_QUEUE_SIZE=12`
- **概要:** 登録できるコールバック関数（`subscribe`）の最大数を指定する設定。
- **解説:** コマンドの種類（バルブ制御、テレメトリ、Ping等）が増えて `subscribe` を多数登録しようとした際、デフォルト上限を超えると後から登録したコマンドが反応しなくなります。これを 12 に増やすことで、多数のコマンドを漏れなく受け付けられるようにしています。

### 3. `-D MSGPACK_MAX_ARRAY_SIZE=12`
- **概要:** MsgPack の1つの配列（リスト）に格納できる要素数の上限設定。
- **解説:** デフォルト上限は 8個です。テレメトリデータ（圧力、電圧、各バルブ状態など）の変数が 9個以上に増えた際、デフォルトのままでは送信時のエンコード処理が失敗してデータが一切送られなくなります。これを回避するために 12 に拡張しています。

## MsgPacketizer のプロトコル仕様 (C++ -> Python)
MsgPacketizer が生成するシリアル通信の1フレームは以下の構造になっている。

```text
[COBS Overhead/Lengths] [Packet ID (Index)] [MsgPack Data Payload] [CRC8] [0x00 (Delimiter)]
```

### 1. COBS (Consistent Overhead Byte Stuffing)
- **仕様:** 
  - フレームの区切り文字として `0x00` を使用する。
  - データペイロード内に `0x00` が含まれる場合、そのまま送信するとフレームの区切りと誤認されるため、COBSエンコードによって `0x00` が排除され、次の `0x00` までの長さを示すバイトに置き換えられる。
- **注意点:** 
  - 受信側（Python）は、MsgPackのデコードを行う**前**に、必ずCOBSデコードを行い、元のペイロードを復元しなければならない。これを怠ると、データ中に `0x00`（例：値が `0` の整数など）が含まれた瞬間にパケットが破損したように見え、以降のデコードが失敗する。

### 2. CRC8 チェックサムの計算範囲
- **仕様:**
  - 多項式: `0x07` (SMBus / FastCRC8::smbus と同等)
  - 計算範囲: **MsgPack データペイロード本体のみ（`packet_id` を除く）**
- **注意点:**
  - Python 側で CRC を計算・検証する際、`[packet_id] + [msgpack data]` の全体に対して CRC を計算すると不一致となる。必ず `packet_id` を除外した `[msgpack data]` 部分に対して CRC8 を計算すること。

### 3. `send()` と `send_arr()` の違いと Python 側の受け皿
- **仕様:**
  - `MsgPacketizer::send()`: 引数を MsgPack の「独立した複数の要素」として直列にエンコードする。
  - `MsgPacketizer::send_arr()`: 引数を MsgPack の「1つの配列（Array）」としてエンコードする。
- **注意点:**
  - 今回実装した Python のシリアルワーカーでは、どちらの関数で送信されても問題なく処理できるように、受信した全要素を Python 側で強制的に1つのリスト `[packet_id, arg1, arg2...]` にパッキング（またはアンラップ）して後続の処理に渡すラッパー機構を実装した。

## 今回発生したトラブルと原因リスト

1. **配列の要素数制限による送信失敗**
   - **症状:** 新たに入力電圧と12Vバス電圧の2つの要素を追加したところ、データが全く送信されなくなった。
   - **原因:** 追加により引数が 9 個となり、デフォルトの `MSGPACK_MAX_ARRAY_SIZE` (8) を超過してエンコードが失敗していた。
   - **解決策:** `platformio.ini` に `-D MSGPACK_MAX_ARRAY_SIZE=12` を追記。

2. **COBS エンコード未対応によるパケット崩壊**
   - **症状:** Python スクリプトでは全くデータを受信できなかった。
   - **原因:** 元の Python スクリプトに COBS デコードが実装されておらず、シリアルの生データを直接 MsgPack デコーダに流し込んでいた。リミットスイッチのダミー値として `0`（`0x00`）を入れた瞬間に COBS によるバイト置換が発動し、MsgPack としての構造が崩壊した。
   - **解決策:** Python スクリプト内に `cobs_decode` および `cobs_encode` を自前で実装し、パケットを抽出してから MsgPack デコーダに渡すように修正。

3. **CRC8 計算範囲の仕様不一致による全破棄**
   - **症状:** COBS デコードを実装しても、依然としてデータが更新されず、Python からの送信コマンドも MCU に無視された。
   - **原因:** Python 側で「パケットID」を含めて CRC8 を計算していたが、C++ 側の Packetizer は「パケットIDを含めず、データ本体のみ」で CRC を計算・照合する仕様だったため。
   - **解決策:** Python の CRC8 計算処理を修正し、`packet_id` を除外した `msgpack` バイト列のみを対象にチェックするように変更した。
